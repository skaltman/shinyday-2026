Auto mode and human review

Anthropic, Auto mode is now the default in Claude Code (August 7, 2026)

Anthropic compared auto mode with human permission review. Auto mode uses a classifier to check tool calls and block dangerous actions, rather than asking the person to approve every command. After a block, Claude can try a safer approach or ask the user; repeated blocks cause fallback to manual approvals. Not every block becomes a human-review prompt.

In a controlled study with 1,053 professional testers, human reviewers blocked 143 dangerous commands (13.6%). Auto mode blocked 937 of those same 1,053 commands (89%). That is auto mode’s own block rate, not a combined model-plus-human catch rate.

One permission prompt per session was replaced with dangerous command text; approving it did not execute the command. Testers were working in a study environment, not their own projects. This shows that auto mode blocked more of these dangerous commands, not that automation is universally safer.

Anthropic subsequently made auto mode the default for eligible plans.

The point is to design review around actual human behavior, not assume that putting a person at every approval step automatically makes a system safer.

Trusted code

This vetted code used by the data scientists is what we’ll called trusted code they rely on it and trust it to give them the right answers

They also might have trusted code in

  • Shiny apps
  • R and Python packages
  • Quarto documents

Instead of the model writing code afresh every time it’s answering a question, what if it could discover and use this trusted code?

This is one of the core ideas behind a new open source package that we’re excited to share with you all today. It’s called commons.

https://pos.it/commons

commons helps data scientists build trustworthy data agents for their collaborators.

It’s an open source R and Python package built on ellmer / chatlas and shinychat. You can use it with whatever model from whatever provider you want.

and it’s a bird because…

commons does 3 things

  • Extract trusted calculations from existing artifacts into a data structure
  • A harness to give the right context at the right time
  • A feedback loop to push more queries up the trust ladder over time

Let’s see how the VP’s analysis would work with a commons agent.

The first thing the agent does is search for a trusted calculation. Here it finds and runs the data scientist’s site traffic calculation.

The answer is marked as verified to signify that it used vetted code.

However, it’s unlikely that trusted code will cover all questions a user might have. For these situations, the agent can write custom R, Python, or SQL.

First, the agent looks through additional context in the form of data dictionaries, markdown files, and, if you have them, existing context layers from Databricks and Snowflake.

Then, it writes whatever code it needs to find an answer.

Finally, when it presents an answer, it can provide a citation to that context. The citation is deterministically checked against trusted context that has appeared in the conversation – if it matches, a citation tag is shown.

There’s one more possible path: the model cannot find trusted context to justify its approach. In this case, we mark the answer with a yellow tag, which lets the user know the answer should be considered less trusted.

This is how we balance convenience and correctness. The tool has to feel convenient enough that the user actually wants to reach for it – it needs to feel like a normal chat. When correctness is closer to a normal coding agent, we signal that the user ought to be more skeptical of the answer.

Commons records which tools produced the answer. Trust is based on that execution path, not on the model’s confidence in its own answer. trust is deterministic

The citation itself is checked against trusted context. A custom answer is not promoted merely because the model says it used a trusted source.

Working with the agent skill

The commons package ships as a skill for coding agents (Posit Assistant, Claude Code, Codex). The skill is named commons; onboarding is one workflow within it, alongside extraction, evaluation, and iteration. The onboarding reference scaffolds the project, collects source material incrementally, and records durable guidance in AGENTS.md / CLAUDE.md.

You don’t have to learn the API cold: the skill knows the package and asks you only for the decisions that matter.

Information layers

Give the agent more than access to data.

Semantic layer Context layer
Trusted calculations the agent can reuse Background information that helps the agent reason about the data
R measures, data dictionary definitions, warehouse metrics Documentation, definitions, conventions, and known limitations

These layers complement the data source. The semantic layer supplies trusted ways to compute answers. The context layer helps the agent write custom SQL or R and interpret the results when a trusted calculation doesn’t cover the question.

Data dictionaries can contribute to both: calculation definitions to the semantic layer, and descriptive information to the context layer.

Build: the semantic layer

Trusted calculations: how an answer is computed.

  • For example: enrollment counts by trial phase, using the team’s agreed definition
  • Reuse vetted R functions as measures, defined inline or in R scripts
  • Or use data dictionary definitions, Snowflake semantic views, and Databricks metric views

The semantic layer collects the vetted calculations the agent prefers to use. Functions documented with @measure become measures; the roxygen description and @param tags become the tool’s description and arguments.

The enrollment example is illustrative, not a statement about J&J’s definitions. The point is to reuse the team’s calculation rather than have the model reinvent its logic for each question. Measures can contain ordinary R code; they do not have to contain SQL or a dbGetQuery call. The same trusted calculations can also come from data dictionary definitions, Snowflake semantic views, or Databricks metric views.

Build: the context layer

Organizational knowledge: what the data means and how to interpret it.

  • For example: what “enrolled” means, reporting conventions, and known data limitations
  • Supply text and Markdown documents; attach structured data dictionaries to data sources
  • Relevant context is retrieved as needed; always-needed guidance goes in instructions

The context layer holds the organizational knowledge that isn’t in the data: definitions, conventions, how tables join, what terms mean. commons searches it when it’s relevant and cites what it used.

Things the agent needs in every conversation – like fiscal-year conventions – go in commons()’ instructions argument instead, so they’re always present.

)

commons_app(agent)

This assembles a chat client, data source, semantic layer, and context layer; commons wraps them with trusted-calculation tools, context search, provenance marking, and a sandboxed R session.

The R/measures.R and context/protocol-conventions.md paths illustrate existing files that supply vetted R measures and organizational context. This is not a self-contained runnable example without those files and its data.

The data source here is a data frame (a clinical trials table), which commons loads into an in-process DuckDB database. The semantic and context layers are optional and grow over time – start with a small working scope and expand.

Build: data sources from the warehouse

# Snowflake semantic view
warehouse <- data_source(
  snowflake_con, tables = "ANALYTICS.TRIAL_ENROLLMENT"
)

# Or: Databricks metric view
warehouse <- data_source(
  databricks_con, tables = "clinical.trial_enrollment_metrics"
)

agent <- commons(
  ellmer::chat_anthropic(),
  data_sources = list(warehouse = warehouse),
  context_layer = context_layer(files = "context/protocol-conventions.md")
)
  • Use existing governed metrics as trusted calculations
  • No separate semantic_layer() call needed for these views

These are illustrative view names, not actual J&J objects. Choose one of the two source definitions; the connections are already configured DBI connections. The Snowflake object is a semantic view, and the Databricks object is a metric view, rather than an ordinary table.

The data source is whatever the data team already maintains in Snowflake or Databricks. Pass a DBI connection and select tables: qualified names like “schema.table”, or a DBI::Id ending in a catalog or schema to select a whole namespace (with exclude globs like “TMP_*” to omit objects).

Namespace selections also import Snowflake semantic views and Databricks metric views as native trusted metrics and dimensions, so warehouse-side definitions become trusted calculations without rewriting them in R. These warehouse semantic models need no separate semantic_layer() call.

Deploy: your colleagues open the app

  • Deploy like any other Shiny app: rsconnect::deployApp()
  • Collaborators ask questions in natural language – no R required
  • Access follows Connect permissions; share_with grants trajectory access

Deployment is ordinary Connect deployment. For trajectory capture, include “OTEL_INSTRUMENTATION_GENAI_CAPTURE_MESSAGE_CONTENT” in deployApp()’s envVars argument, and a server administrator must enable OpenTelemetry.Enabled and OpenTelemetry.AllowContentInstrumentation.

Users whose Connect account role is viewer cannot read traces even when named in share_with; trace readers need at least a publisher account.

Governance

  • Enforce access with warehouse permissions and per-viewer credentials
  • Restrict provider-visible data, context, results, and measure source
  • Protect full-conversation trajectory logs with access controls and retention

https://posit-dev.github.io/commons/r/articles/governance.html

Tables describe data; they do not authorize access. Create DBI connections and the agent inside the Shiny server for each session, using Connect viewer OAuth. The supplied connection enforces warehouse row-level security and table- and column-level policies.

A shared service account has the same database permissions for every user; it does not automatically differentiate users.

Snowflake and Databricks integration

  • data_source() works with data frames, pins boards, and DBI connections
  • Snowflake semantic views and Databricks metric views are read as trusted measures
  • Queries against them execute natively in the warehouse, under the connection’s permissions
  • Answers built on them are marked trusted; custom code is marked differently

The integration works with what your warehouse team already maintains: the semantic layer lives in Snowflake or Databricks, and commons reads its measures and dimensions rather than copying them into the agent.

Metrics execute in the warehouse under the connection’s permissions. commons queries the existing database rather than loading the source into its own DuckDB database; query results can still be returned to the agent. Native trusted metric execution is available in the R package; do not imply Python parity without checking.

Improve: the trajectory reviewer

  • commons(log = TRUE) records conversation histories with OpenTelemetry
  • trajectory_read() reads trajectories from Connect or local traces
  • trajectory_review() opens a Shiny app to browse, flag, and annotate conversations

We’ll demo the trajectory reviewer here. Reviewed conversations surface recurring questions, then you add trusted calculations or context. The goal is to improve the system, not just ask users to check answers more carefully. These reviewer functions are in the R package.

Reading trajectories back into R

# All trajectories you can access

# A recent window

# Deployed content, by Connect GUID or URL

trajectory_read() pulls captured conversations into a data frame; trajectory_review() launches a Shiny app over them. Review output feeds back into the Build stage as new trusted calculations and context.
